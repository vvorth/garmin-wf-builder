# Probe: static content in an offscreen `BufferedBitmap`

**Answers, up front.**

| | question | answer |
|---|---|---|
| **a** | does a no-palette buffer cleared with `setColor(fg, COLOR_TRANSPARENT); clear();` blit with its unset pixels transparent, on a device with `alphaBlendingSupport: false`? | **Cannot be established.** The SDK does not say, and it cannot be run here. So the **opaque** design shipped -- see below. |
| **b** | does `Graphics.createBufferedBitmap({...}).get() as BufferedBitmap?` compile under `-l 3`? | **Yes**, warning-free on `fenix8solar47mm`, `fenix8solar51mm` and `fr955`, SDK 9.2.0. |
| **c** | what does the idiom cost? | **+9 B data, +147 B code** for the idiom alone (+27 / +183 on a real design), plus one full-screen buffer in the *separate* graphics pool -- 67,600 B of 1,048,576 B at 260x260. |

---

## a. Transparency: asked, and deliberately not relied on

The attractive version of this feature lets a static group sit anywhere in draw
order: allocate a buffer with no `:palette`, clear it to `COLOR_TRANSPARENT`,
draw the static elements into it, and blit it between two dynamic ones. That
needs the blit to leave the untouched pixels alone.

What the SDK actually says, all of it:

* `Dc.clear()` -- "Starting form version 3.1.0, COLOR_TRANSPARENT will also be
  honored as background color, which will cause the value of pixels in the clip
  region to be replaced by COLOR_TRANSPARENT. For example, this can be used to
  clear the transparent overlay layer so animation background is visible."
  (`$CIQ_SDK/doc/Toybox/Graphics/Dc.html`). The example given is the WatchUi
  *overlay layer*, not a `BufferedBitmap`.
* `Graphics.AlphaBlending` -- `ALPHA_BLENDING_FULL` is the "Default surface for
  buffered bitmap with maximum alpha blending support"
  (`$CIQ_SDK/doc/Toybox/Graphics.html`, API 4.0.0). That is about drawing *into*
  the buffer with 32-bit AARRGGBB through `Dc.setFill`/`setStroke`; nothing on
  that page says what happens when the buffer is drawn *out* to a screen.
* Core Topics -- "Bitmaps with a palette that are generated by the **resource
  compiler** will have an additional transparent index at the end of the
  specified palette unless the disableTransparency flag has been specified"
  (`$CIQ_SDK/doc/docs/Core_Topics/Graphics.html`). This is the one place the SDK
  explains where a transparent index comes from, and it is explicitly about
  resource bitmaps -- not about a surface from `createBufferedBitmap`.
* `Dc.drawBitmap` documents no transparency behaviour at all.
* `alphaBlendingSupport` does not appear anywhere under `$CIQ_SDK/doc/`
  (`grep -r`). It is a `compiler.json` key with no published semantics, and it
  is `false` on all three targets.

The one piece of evidence pointing the *other* way, recorded because leaving it
out would make this look more one-sided than it is: each target's `compiler.json`
says `"pixelFormat": "ARGB2222"`, i.e. the display's own 8-bit pixel carries two
alpha bits. So a transparent pixel is *representable* on this hardware, which is
also why palette bitmaps with a transparent index render correctly on it. What
is still missing is any statement that a no-palette `createBufferedBitmap`
allocates in that format, or that `drawBitmap` honours those bits when
`alphaBlendingSupport` is false. Suggestive is not decisive, and the difference
between the two is exactly what this project has been burned by before.

The symbol table is no help here either, and says so loudly: `Dc.setFill`,
`Dc.setStroke` and `Dc.setBlendMode` are **all present** on all three targets'
own `<id>.api.debug.xml` despite `alphaBlendingSupport: false`. That is CLAUDE.md
constraint 6b in miniature -- a symbol being callable is not evidence about what
it does.

There is no simulator in this container (CLAUDE.md finding 11), so the runtime
behaviour is not observable. **UNVERIFIED**, and treated the way the
`complication-pull` probe treated its own open question: not built on.

### What shipped instead

**The opaque design.** A static group is a **contiguous prefix of draw order**,
its buffer is opaque and full-screen, and everything else draws over the blit.
This needs no transparency at all: blitting an opaque full-screen bitmap at
`(0, 0)` before anything else is drawn is, pixel for pixel, the same as having
drawn those elements onto the screen -- which is exactly what the fallback path
does when there is no buffer.

Two consequences worth stating plainly, because they are restrictions the
transparent design would not have had:

* Static content must come **first**. `wfb` enforces it (`error[static]`,
  `wfb/ir.py::Builder._check_static_order`) rather than letting a blit silently
  erase whatever was drawn under it.
* All static content shares **one** buffer. Two opaque full-screen buffers
  cannot coexist -- the second would erase the first -- so several `static:`
  groups are allowed only where they are contiguous at the front, and they fill
  one buffer between them.

If someone can later demonstrate transparency on real hardware, the prefix rule
is the only thing that has to relax; the codegen shape does not change.

## b. The generated shape compiles

`ProbeView.mc` is the exact code the emitter now writes, by hand: the
`Graphics has :createBufferedBitmap` guard, the `.get()` lock, the null field,
the `getDc()` fill in `onLayout`, and the `drawBitmap(0, 0, buffer)` /
`renderStatic(dc)` fork in `onUpdate`.

```
$CIQ_SDK/bin/monkeyc -f monkey.jungle -d <device> -o probe.prg \
    -y ~/ciq/developer_key.der -w -l 3
BUILD SUCCESSFUL            # fenix8solar47mm, fenix8solar51mm, fr955
```

Two things this settles that the doc pages do not:

* **`as BufferedBitmap?` is accepted.** The Analog sample
  (`$CIQ_SDK/samples/Analog/source/AnalogView.mc:69`) writes the non-nullable
  `as BufferedBitmap`. The generator needs the nullable form, because the field
  really can be null on a device with no `createBufferedBitmap`. It typechecks.
* **The narrowing has to go through a local.** `if (_static != null)
  { _static.getDc(); }` is *not* enough; the strict typechecker only narrows a
  local, so the generator copies the field first. Confirmed by watching it fail:

  ```
  ERROR: fenix8solar47mm: ProbeView.mc:29,12: Cannot find symbol ':getDc' on type 'Null'.
  ```

  That negative control is also what proves `-l 3` is genuinely running here
  rather than being silently skipped.

`BufferedBitmapReference.get` does not appear in any target's
`<id>.api.debug.xml` under that class -- it is inherited from
`Graphics.ResourceReference`, which *is* present on all three. `Device.has_symbol`
answers False for the derived spelling and True for the base one; the build is
what settles it.

### Why `.get()` and not the reference

`$CIQ_SDK/doc/docs/Core_Topics/Graphics.html`: "Unlike static resources that are
reloaded from your executable, `Graphics.BufferedBitmap` are **not restored if
they have been purged**. ... Alternatively, you can call the `get()` method on
the reference to get a locked version of the bitmap. This will prevent the
`BufferedBitmap` object from being purged from the pool."

A static buffer is filled exactly once, in `onLayout`, and read every frame
afterwards. A purge would blank the face and nothing would refill it, so the
lock is not an optimisation here, it is correctness -- and it is why the
`graphics-pool` lint exists: a locked buffer is pool space that cannot be
reclaimed.

## c. What it costs

Measured on this probe, `-l 3 -O 3z --build-stats 0`, against a variant that
draws exactly the same content straight to the screen with no buffer and no
field:

| | data (fg) | code (fg) | `.prg` |
|---|---|---|---|
| without buffer | 761 B | 886 B | 94,604 B (47 mm) |
| with buffer | 770 B | 1,033 B | 94,972 B (47 mm) |
| **delta** | **+9 B** | **+147 B** | **+368 B** |

Identical on all three targets to the byte for data and code; the `.prg` differs
by the 51 mm's larger resources (95,052 B with, 94,684 B without). The absolute
`.prg` size is large because the probe reuses the slice example's scaffold,
fonts and all -- only the delta is about the buffer.

Measured again end to end on a real design, `examples/static/face.yaml` against
a hand-written twin that draws the identical picture with no buffer at all (the
two `wfb preview` renderings are pixel-identical):

| | data (fg) | code (fg) | app total | `.prg` |
|---|---|---|---|---|
| without buffer | 892 B | 1,877 B | 2,769 B | 96,140 B |
| with buffer | 919 B | 2,060 B | 2,979 B | 96,812 B |
| **delta** | **+27 B** | **+183 B** | **+210 B** | **+672 B** |

Identical to the byte on `fr955`, and within 1 B on `fenix8solar51mm`. 2,979 B
is 2.3% of the 131,072 B watch-face limit.

The isolated measurement above was taken with `renderTransparentProbe` deleted. It is dead code
that documents question (a)'s compile half and `-O 3z` does **not** strip it
(leaving it in costs a further 9 B data / 28 B code), so the honest delta for the
idiom the generator actually emits excludes it.

**The buffer itself is not in that budget.** 260x260 and 280x280 full-screen
surfaces come from the graphics pool, which is 1,048,576 B on all three targets
(`graphicsResourcePoolSize`, `wfb/devices.py::graphics_pool_bytes`), separate
from the 131,072 B watch-face app limit. Each target's `compiler.json` says
`"bitsPerPixel": 8`, so one byte a pixel is the best-grounded figure available:
**67,600 B** on a 260x260 screen and **78,400 B** on 280x280 -- 6.4% and 7.5% of
the pool. That is what `wfb`'s `graphics-pool` lint sums, and it still calls
itself an *estimate* (ADR 0008), because `bitsPerPixel` describes the **display**
and the SDK nowhere says that a no-palette `createBufferedBitmap` allocates in
that format, nor what per-surface overhead the pool adds.

## What this probe does NOT settle

* **Whether any of this is faster.** The whole point of the feature is CPU and
  battery, and there is no simulator and no watch here. Nothing in this repo has
  measured a speedup and nothing should claim one. What is verified is that it
  compiles, that the no-buffer fallback exists and draws the same content, and
  what it costs in bytes.
* **Transparency** -- question (a), above.
* **Whether the pool ever refuses the allocation.** `createBufferedBitmap` is
  documented to throw only for a bad palette or a bad bitmap resource; an
  out-of-pool `Graphics.OutOfGraphicsMemoryException` type exists
  (`$CIQ_SDK/doc/Toybox/Graphics/OutOfGraphicsMemoryException.html`) but is not
  listed on `createBufferedBitmap`'s own Throws list. The generator's null check
  on `.get()` covers a null return; it does not catch a throw, because the SDK
  does not document one on this call.

## Reproducing

Source-only, like the sibling probes. Drop `ProbeView.mc` into a minimal
watch-face project (the easiest scaffold is a `wfb build` output directory with
its generated `*View.mc` replaced and the app's `getInitialView` pointed at
`ProbeView`), then:

    $CIQ_SDK/bin/monkeyc -f monkey.jungle -d fenix8solar47mm \
        -o probe.prg -y ~/ciq/developer_key.der -w -l 3 --build-stats 0
