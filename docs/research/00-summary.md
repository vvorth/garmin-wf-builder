## The five findings that should change your plan

**1. The build is not blocked the way the sibling project claims — but device
definitions are.** `developer.garmin.com` serves the SDK unauthenticated
(`sdks.json` → a 204 MB zip), and `monkeyc` runs fine on OpenJDK 25. What is
gated is the **per-device definitions**, fetched by the SDK Manager from
`api.gcs.garmin.com/ciq-product-onboarding/devices`, which returns **401** — a
Garmin SSO requirement, not a network block. Without them, `monkeyc -d
fenix8solar47mm` fails with `Invalid device id specified`. Everything else in the
toolchain is available. *(This also means the Dashboard project's `CLAUDE.md` is
wrong on two counts and should be corrected.)*

**2. Your tap-to-cycle requirement does not reach the fr955.** Your prompt states
`onTap`/`onPress` are "4.2.0+ on touch devices". The SDK says otherwise:

| Method | Since | fenix8solar 47/51 | fr955 |
|---|---|---|---|
| `onPress` (touch **and hold**) | 4.2.0 | yes | **yes** |
| `onTap` (touch) | **5.1.0** | yes | **NO** |

Verified by explicit enumeration of the documented device lists:
`Forerunner® 955 / Solar` appears under `onPress` and is absent from `onTap`.
So "tap a data slot to cycle it" works on both fēnix 8 Solar targets and not on
the fr955, where the closest equivalent is touch-and-hold. **This needs your
decision** — see §"Decisions I need" below.

**3. On-device configuration is real but far narrower than the requirement
implies.** The native editor (API **5.1.0**, fēnix 8 and newer — so **not
fr955**) exposes exactly four axes: **Styles** (enumerated variants),
**Data** (complication slots), **one Data Colour**, **one Accent Colour**, with a
maximum of **four saved configurations**. There is no per-element colour editing
and no arbitrary data binding. "Colours and displayed data changeable from the
watch" is therefore *partially* satisfiable, and anything beyond those four axes
must fall back to on-device settings menus, phone settings, or `Storage`.

**4. Connect IQ has no filled-arc primitive at all.** An exhaustive grep of the
API surface finds no `fillArc`, `fillSector`, or `drawSector`. Progress rings
must be `setPenWidth` + `drawArc`, which fixes thickness semantics, removes cap
control, and makes true annuli/gradient sweeps a polygon-approximation problem.
Compounding this, `setAntiAlias` is **not supported on a palette'd
`BufferedBitmap`** — so smooth thick arcs and cheap off-screen buffers are
mutually exclusive. The schema must not promise a "ring" that the platform
cannot draw.

**5. There is no device-side renderer, which decides the architecture.** Every
comparable declarative format (WFF, Facer, Fitbit) relies on a renderer already
present on the device. Garmin ships none. So the format must compile to Monkey C
ahead of time, or ship an interpreter *inside the same 128 KB the design must fit
in*. Combined with Garmin's native `excludeAnnotations` dead-code mechanism —
which only a generator can exploit — this points hard at codegen. ADR 1.2 will
argue it properly, but the evidence is already one-sided.

## Scope flags

Raised now rather than discovered later:

- **fr955 is a second-class target** for two headline features (tap, on-device
  config). Any plan that treats the three targets as interchangeable is wrong.
- **AMOLED is most of the market** (74/164 devices) and has a *structurally*
  different low-power path — `onPartialUpdate` is forbidden there. Your targets
  are all MIP, so this can be deferred, but the IR must reserve room for it or a
  later retrofit will be painful.
- **28 of 164 devices cannot run a watch face at all.** "Supports watch faces"
  must be a predicate in the device database, not an assumption.
- **The escape hatch is not optional.** WFF's main developer backlash was the
  expressiveness ceiling of pure declaration. Since we cannot force migration,
  the format needs a defined way to drop to hand-written Monkey C for one
  element. I recommend this becomes its own ADR in Phase 1.
- **No established Garmin watch-face framework exists.** The nearest precedent
  (`tobwil/garmincreator`) is 4 commits and 4 devices, and stalled precisely at
  device breadth. That is the opportunity and the warning.

## Decisions I need from you before Phase 1

1. **fr955 interaction model.** Cycle on *hold* everywhere (one model, all three
   devices, diverges from the stock-face feel); or *tap* where available with
   *hold* as the fr955 fallback (best feel, two generated paths); or drop the
   fr955 from interactive slots. I lean toward the second — the framework
   generating both paths from one declaration is exactly the value proposition.

2. **How much on-device configurability do you actually need?** If one data
   colour plus one accent colour genuinely covers it, the native editor is
   enough. If you want per-element colour control on the wrist, that needs a
   generated on-device settings menu instead, which is more work and a different
   UX. This materially changes the config schema in ADR 1.3.

3. **Confirm the host language.** You said "you choose, justify it, but not
   TypeScript/Node". I intend to recommend **Python** in an ADR — it is already
   the toolchain language in your sibling project (`tools/preview.py`,
   `tools/make_clock_font.py`), it has the imaging and font libraries the asset
   pipeline needs (Pillow, fontTools), and it keeps the preview renderer and the
   compiler in one language so they can share the layout IR. Say now if you'd
   rather it were Rust or Go, because it is expensive to change later.

Phase 1 ADRs are drafted next, and per your working agreement I will not start
framework code until you have reviewed this.
